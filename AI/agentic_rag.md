# Agentic RAG

Agentic RAG는 검색 결과를 그대로 사용해 답변하는 고정형 RAG와 달리, 모델 또는 그래프가 질문과 검색 결과를 평가하면서 다음 행동을 선택하는 구조다. 검색이 필요한지 판단하고, 적절한 검색 도구를 호출하며, 결과가 충분하지 않으면 질문을 다시 작성하거나 재검색할 수 있다.

## 일반 RAG와 Agentic RAG

일반적인 RAG의 흐름은 다음과 같이 비교적 고정되어 있다.

```text
질문 → 검색 → 검색 결과를 포함한 답변 생성
```

Agentic RAG는 검색 전후에 판단 단계를 추가한다.

```text
질문
  ↓
검색 필요성 판단
  ├─ 불필요 → 직접 답변
  └─ 필요 → 검색 → 결과 평가
                    ├─ 충분 → 근거 기반 답변
                    └─ 부족 → 질문 재작성·재검색 또는 답변 보류
```

둘은 서로 배타적인 개념이 아니다. Agentic RAG는 RAG에 판단, 평가, 재시도, 도구 선택 같은 제어 흐름을 추가한 확장된 설계로 볼 수 있다.

## 핵심 구성 요소

### 검색 여부 판단

모든 질문에 검색을 적용하면 불필요한 지연과 비용이 발생할 수 있다. 모델이 질문의 성격과 현재 대화 내용을 바탕으로 검색 도구를 호출할지, 이미 알고 있는 범위에서 답변할지 선택하게 할 수 있다.

검색을 사용하는 편이 적절한 경우는 다음과 같다.

- 특정 문서나 내부 데이터에 근거해야 하는 질문
- 최신 정보나 변경 가능한 정보가 필요한 질문
- 답변의 출처와 근거가 필요한 질문
- 모델의 일반 지식만으로 판단하기 어려운 도메인 질문

### 검색 도구

검색기는 Agent가 호출할 수 있는 Tool 형태로 감싸는 경우가 많다. Tool은 검색어를 받아 문서 목록과 메타데이터를 반환하며, 검색 결과에는 페이지 번호·문서 ID·출처 같은 추적 정보를 함께 포함하는 것이 좋다.

검색 방식은 하나로 제한되지 않는다.

- 벡터 검색: 의미가 유사한 문서를 찾는 방식
- 키워드 검색: 고유명사, 숫자, 정확한 용어에 강한 방식
- 하이브리드 검색: 벡터 검색과 BM25 같은 키워드 검색을 결합
- 메타데이터 필터링: 날짜, 문서 유형, 권한, 부서 등으로 검색 범위 제한

### 검색 결과 평가

검색 결과가 반환되었다는 사실만으로 답변 근거가 충분한 것은 아니다. 원래 질문과 검색 문서 사이의 관련성, 질문에 필요한 구체적 정보의 포함 여부, 서로 충돌하는 정보의 존재 여부를 확인해야 한다.

평가 결과는 단순한 참·거짓보다 다음과 같은 상태로 구분할 수 있다.

```text
관련성 있음       → 답변 생성
관련성 부족       → 질문 재작성 또는 다른 검색기 사용
근거 확인 불가    → 재시도 횟수 확인 후 답변 보류
```

평가 모델의 출력은 구조화된 값으로 제한하는 것이 좋다. 예를 들어 `relevant: bool`, `reason: str`, `missing_information: list[str]` 같은 필드를 사용하면 그래프 분기 조건을 안정적으로 관리할 수 있다.

### 질문 재작성

사용자 질문은 검색에 적합하지 않은 표현을 포함할 수 있다. 질문 재작성은 원래 의도를 유지하면서 문서에 등장할 가능성이 높은 용어와 범위로 검색어를 바꾸는 과정이다.

재작성 시 주의할 점은 다음과 같다.

- 원래 질문의 핵심 의도를 바꾸지 않는다.
- 대명사나 생략된 표현을 가능한 범위에서 구체화한다.
- 검색 결과에 없는 내용을 임의로 사실처럼 추가하지 않는다.
- 재작성 횟수와 전체 검색 비용을 제한한다.

### 답변 보류

검색을 반복해도 근거가 부족하다면 답변을 생성하지 않는 경로가 필요하다. 근거가 없는 답변을 억지로 생성하는 것보다, 찾지 못한 정보와 답변할 수 없는 이유를 명확하게 전달하는 편이 신뢰성 측면에서 안전하다.

보류 응답에는 다음 정보를 포함할 수 있다.

- 확인된 문서 범위
- 부족한 근거
- 추가로 필요한 정보
- 사용자가 질문을 좁히거나 제공할 수 있는 자료

## 그래프 설계

Agentic RAG는 상태와 분기 조건을 가진 그래프로 표현하기 적합하다. 상태에는 대화 메시지뿐 아니라 원래 질문, 재시도 횟수, 검색 결과 평가 상태, 종료 이유 등을 저장할 수 있다.

```text
START
  ↓
generate_query_or_respond
  ├─ 직접 답변 → END
  └─ retrieve
       ↓
   grade_documents
    ├─ generate_answer → END
    ├─ rewrite_question → 검색 판단 노드
    └─ abstain → END
```

`original_question`을 별도로 보존하면 질문을 여러 번 재작성하더라도 최종 답변의 기준이 되는 원래 의도를 잃지 않는다. `retry_count`는 무한 재검색을 방지하며, `termination_reason`은 운영 환경에서 종료 원인을 추적하는 데 사용된다.

## HyDE와 확장 전략

HyDE(Hypothetical Document Embeddings)는 질문에 대한 가상의 답변 문단을 생성한 뒤, 그 문단을 검색어처럼 사용해 의미적으로 가까운 실제 문서를 찾는 전략이다. 가상 문서는 검색어 생성에만 사용하며 최종 답변의 근거로 사용해서는 안 된다.

그 밖에 다음 전략을 조합할 수 있다.

- Multi-query: 하나의 질문에서 여러 검색어를 생성
- 질문 분해: 복합 질문을 여러 하위 질문으로 나눠 검색
- 병렬 검색: 서로 다른 검색기나 컬렉션을 동시에 조회
- 검색 도구 선택: 질문 유형에 따라 검색기 선택
- 부족한 정보 중심 재검색: 평가 결과에서 누락된 부분만 다시 검색
- 답변 주장 검증: 생성된 답변의 각 주장과 문서 근거를 대조

## 설계 시 주의점

### 재시도 제한

검색 결과가 부족할 때 무조건 반복하면 지연과 비용이 급격히 증가한다. 최대 재시도 횟수, 전체 실행 시간, 검색 결과의 최소 품질 기준을 함께 설정해야 한다.

### 검색 결과와 지시문 분리

검색 문서는 신뢰할 수 없는 데이터로 취급해야 한다. 문서 안에 포함된 명령형 문장이 시스템 지시를 덮어쓰지 않도록 프롬프트에서 문서의 역할을 명확히 제한한다.

### 근거의 출처 보존

문서 내용만 이어 붙이면 답변 출처를 추적하기 어렵다. 문서 ID, 페이지, chunk ID, 검색 점수 등을 함께 보존하면 답변 검증과 사용자용 인용 생성에 활용할 수 있다.

### 실패를 정상 경로로 취급

검색 실패, 근거 부족, 도구 오류는 예외 상황으로만 처리하지 말고 그래프의 명시적인 분기와 종료 상태로 설계하는 편이 좋다. 그래야 사용자는 불확실한 답변과 답변 보류를 구분할 수 있다.

### 평가 기준 분리

검색 결과의 관련성, 답변의 정확성, 답변의 근거 충실도는 서로 다른 평가 대상이다. 하나의 점수로 통합하기보다 단계별로 측정하면 어느 부분에서 품질이 떨어지는지 파악하기 쉽다.
