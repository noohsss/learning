# RAG 평가

## RAG 평가가 필요한 이유

RAG는 검색 결과와 생성 답변을 나누어 평가해야 한다.

```text
검색기가 정답 근거를 찾았는가? → 검색 평가
검색된 근거로 좋은 답변을 만들었는가? → 답변 평가
```

청크 크기, 검색 문서 수(`k`), Similarity·MMR·BM25·Hybrid 중 어떤 전략을 사용할지 대표 질문 몇 개만 보고 결정하면 주관적이다. 같은 평가 데이터셋과 조건으로 여러 번 측정해야 한다.

## 평가 방법

| 방법 | 특징 | 사용 시점 |
|---|---|---|
| 수동 확인 | 질문과 답변을 직접 읽음 | 초기 개발, 빠른 검증 |
| 검색 지표 | Hit@k, Precision@k, Recall@k, MRR | 검색 설정 비교 |
| RAGAS | LLM과 embedding으로 답변 평가 | 근거성·관련성 평가 |
| LLM-as-Judge | 도메인 기준을 직접 정의 | 정확성·완전성 평가 |
| 사용자 피드백 | 실제 사용자의 반응 수집 | 서비스 운영 |

## 평가 데이터셋

평가 데이터는 질문, 기대 정답, 정답 문서를 사람이 미리 작성한 기준 데이터다.

| 필드 | 설명 |
|---|---|
| `user_input` | 사용자 질문 |
| `reference` | 사람이 작성한 기준 정답 |
| `relevant_sources` | 정답이 포함된 문서 파일 |
| `retrieved_contexts` | 검색된 문서 내용 |
| `response` | RAG가 생성한 답변 |

검색 평가는 질문·정답 문서·검색 결과만 있으면 된다. 답변 평가는 검색 문서, 생성 답변, 기준 정답까지 필요하다.

평가 질문은 `easy`, `medium`, `hard`를 섞는다. 쉬운 질문만 사용하면 점수가 부풀고, 어려운 질문만 사용하면 기본 검색 문제와 여러 문서가 필요한 문제를 구분하기 어렵다.

검색기는 청크를 반환하지만 정답은 파일 단위로 관리할 수 있다. 이때 청크의 `metadata["source"]`가 정답 파일 목록에 포함되는지 확인한다.

## 평가 순서

```text
질문과 정답 문서 준비
→ 검색기 실행
→ Hit@k·Precision@k·Recall@k·MRR 측정
→ 검색 context로 답변 생성
→ 인용 검사·RAGAS·LLM-as-Judge 실행
→ 품질 점수와 latency 비교
```

검색 실패와 답변 생성 실패를 구분하기 위해 검색 평가부터 수행한다.

## 검색 지표

### Hit@k

상위 `k`개 결과 안에 정답 문서가 하나라도 있는지 확인한다.

```text
Hit@k = 정답 문서가 있으면 1, 없으면 0
```

### Precision@k

상위 `k`개 검색 결과 중 관련 문서의 비율이다.

```text
Precision@k = 상위 k개 중 관련 결과 수 / 상위 k개 결과 수
```

### Recall@k

필요한 전체 정답 문서 중 상위 `k`개에서 찾은 비율이다.

```text
Recall@k = 상위 k개에서 찾은 정답 문서 수 / 전체 정답 문서 수
```

같은 source의 청크가 여러 번 검색돼도 하나의 문서로 계산한다.

### RR과 MRR

RR(Reciprocal Rank)은 첫 번째 정답 문서가 나온 순위의 역수다.

```text
RR = 1 / 첫 번째 정답 문서의 순위
MRR = 모든 질문의 RR 합 / 전체 질문 수
```

정답 문서가 검색 결과 앞쪽에 나올수록 1에 가까워진다.

## 검색 전략 비교

모든 전략에 같은 문서, 질문, 후보 개수를 적용해야 한다.

- **Similarity**: 질문과 의미가 가까운 문서 검색
- **MMR**: 관련성과 결과 간 다양성을 함께 고려
- **BM25**: 실제 단어 일치 기반 검색
- **Hybrid**: 벡터 검색과 BM25의 순위 결합

질문마다 `hit@1`, `hit@3`, `hit@5`, `precision@5`, `recall@3`, `recall@5`, `RR`, `latency`를 기록한다.

전체 평균뿐 아니라 `easy`, `medium`, `hard` 난이도별 결과도 확인한다. `Recall@5 < 1`인 실패 질문을 따로 출력해 어떤 정답 문서를 놓쳤는지 확인한다.

품질이 비슷하면 latency와 구현 복잡도가 낮은 전략을 선택한다. 복잡한 전략이 항상 더 좋은 결과를 보장하지는 않는다.

## 답변 생성과 인용 검사

검색 문서를 context로 구성해 LLM에 전달하고, 답변과 사용한 출처를 구조화된 형태로 받는다.

```python
class GroundedAnswer(BaseModel):
    answer: str
    citations: list[str]
```

- `valid_citation`: 인용한 파일이 실제 검색 결과에 포함되는가
- `relevant_citation`: 인용한 파일 중 정답 문서가 하나 이상 있는가

이 검사는 출처의 존재와 일치만 확인한다. 문장별 주장이 문서와 맞는지, 질문에 충분히 답했는지는 판단하지 못한다.

## RAGAS

RAGAS는 RAG 검색 결과와 생성 답변을 LLM과 embedding으로 평가하는 라이브러리다.

```python
{
    "user_input": "사용자 질문",
    "response": "생성 답변",
    "retrieved_contexts": ["검색 문서"],
    "reference": "기준 정답",
}
```

| 메트릭 | 확인 내용 |
|---|---|
| Faithfulness | 답변의 주장이 검색 문서로 뒷받침되는가 |
| Answer Relevancy | 답변이 질문의 핵심과 관련되는가 |
| Context Precision | 유용한 문서가 검색 결과 앞쪽에 있는가 |
| Context Recall | 기준 정답에 필요한 내용이 검색됐는가 |
| Factual Correctness | 답변의 사실이 기준 정답과 일치하는가 |
| Semantic Similarity | 답변과 기준 정답의 의미가 비슷한가 |

Faithfulness가 높아도 검색 문서 자체가 틀리면 정답이라는 뜻은 아니다. Answer Relevancy도 질문과의 관련성만 볼 뿐 사실 여부를 보장하지 않는다.

| Faithfulness | Answer Relevancy | 해석 |
|---|---|---|
| 높음 | 높음 | 근거를 사용해 질문에 답함 |
| 높음 | 낮음 | 근거에는 맞지만 질문에서 벗어남 |
| 낮음 | 높음 | 질문에는 답하지만 근거 밖 내용을 생성 |
| 낮음 | 낮음 | 근거성과 관련성이 모두 부족 |

RAGAS 점수는 절대 합격선보다 같은 평가셋에서 설정을 비교하는 용도로 사용한다.

## LLM-as-Judge

도메인 기준을 직접 작성해 LLM에게 채점을 맡긴다.

- `correctness`: 기준 정답과 사실이 맞는가
- `completeness`: 필요한 조건과 예외를 포함했는가
- `groundedness`: 검색 문서에 근거가 있는가
- `citation_accuracy`: 인용 출처가 실제 내용을 지지하는가

각 항목을 1~10점으로 평가하고 평균뿐 아니라 감점 이유도 저장한다. “좋은 답변인가?”보다 수치, 조건, 누락, 근거 여부를 구체적으로 정의한다.

## 비용과 운영

검색 지표는 LLM 호출 없이 계산할 수 있어 반복 실행하기 좋다. 답변 생성, RAGAS, LLM-as-Judge는 질문 수와 메트릭 수만큼 API 호출과 비용이 늘어난다.

- 개발 중: 전체 검색 평가를 자주 실행
- 생성 평가: 난이도별 대표 문항부터 실행
- RAGAS·Judge: 필요한 메트릭만 선택
- 결과 기록: 품질 점수와 latency를 함께 저장
- 문서 변경: 관련 질문과 정답 출처 재검증
- 운영: 실패 질문을 평가셋에 추가

평가 데이터셋은 문서와 검색 전략이 바뀔 때마다 실패 사례와 기준 정답을 갱신한다.
