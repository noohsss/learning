# LangGraph Agent 평가

Agent 평가는 사용자 요청에 대한 최종 답변과 내부 처리 과정을 기대값과 비교해 품질을 측정하는 작업이다. 단순히 답변이 자연스러운지 확인하는 것이 아니라, 필요한 Tool이 실행되었는지, 잘못된 Tool은 실행되지 않았는지, 승인 절차가 지켜졌는지까지 평가 범위를 확장할 수 있다.

## 평가 흐름

```text
입력·기대값 준비 → Agent 실행 → 실제 결과 수집 → 평가자 채점 → Experiment 비교
```

- **Dataset**: 평가에 사용할 입력과 기대 결과의 모음
- **Target**: Dataset의 입력을 받아 Agent를 실행하는 함수
- **Evaluator**: 실제 결과와 기대 결과를 비교해 점수와 근거를 반환하는 함수
- **Experiment**: 하나의 Dataset 전체를 실행하고 결과와 점수를 기록한 평가 실행

모델, Prompt, Tool, Agent 코드를 변경한 뒤 동일한 Dataset과 평가 기준으로 다시 Experiment를 실행하면 변경 전후의 품질을 비교할 수 있다.

## Golden Set

Golden set은 각 입력에 대해 기대하는 답변과 처리 기준을 사람이 검토해 정리한 평가 사례 모음이다. 정확한 정답 문장만 저장할 수도 있고, 답변에 반드시 포함되어야 할 사실과 해서는 안 되는 행동을 기준으로 저장할 수도 있다.

좋은 Golden set은 정상 요청만 포함하지 않는다.

- 정보가 부족한 요청
- 처리할 수 없는 요청
- 권한 경계에 있는 요청
- 승인과 거절이 필요한 요청
- 잘못된 인자나 금액이 포함된 요청
- 외부 상태를 변경하는 요청

기대 결과에 영향을 주는 초기 데이터와 실행 조건도 함께 기록해야 한다. Agent가 실행될 때마다 다른 초기 상태를 사용하면 결과 비교가 어려워지므로, 동일한 조건에서 시작하도록 구성한다.

## 답변 평가

답변 평가는 최종 응답이 사용자 요청과 기대 기준을 충족하는지 확인한다. 의미가 같은 표현을 허용하려면 LLM-as-a-Judge를 사용할 수 있다.

답변 평가 시 다음을 확인한다.

- 질문에 필요한 사실을 포함하는가
- 수치, 계좌, 날짜 같은 핵심 값이 정확한가
- 승인되지 않은 작업을 완료했다고 말하지 않는가
- 정보가 부족할 때 임의로 추측하지 않는가
- 거절된 작업을 완료된 것으로 안내하지 않는가

LLM 평가자는 표현의 차이를 어느 정도 허용할 수 있지만, 평가 결과 자체도 검토가 필요하다. 평가 모델이 잘못된 기대 기준을 그대로 통과시키지 않도록 점수와 판단 근거를 함께 확인해야 한다.

## Trajectory 평가

Trajectory는 Agent가 실행되는 동안 거친 처리 과정의 기록이다. 최종 답변만으로는 알 수 없는 Tool 호출, 인자, 호출 순서, 승인 중단을 평가할 수 있다.

주요 평가 항목은 다음과 같다.

- **필수 Tool**: 반드시 실행되어야 하는 Tool이 호출되었는가
- **핵심 인자**: 계좌 ID, 금액 등 중요한 인자가 올바른가
- **허용 Tool**: 허용되지 않은 Tool이 실행되지 않았는가
- **호출 순서**: 필요한 순서로 Tool이 실행되었는가
- **승인 흐름**: 기대한 횟수와 대상 Tool에서 승인·거절이 처리되었는가
- **종료 상태**: 처리하지 못한 승인 대기가 남아 있지 않은가

## Trajectory 비교 모드

Trajectory 평가에서는 기대 호출과 실제 호출을 비교하는 기준을 선택할 수 있다.

| 모드 | 의미 |
|---|---|
| `strict` | 호출 목록과 순서가 정확히 일치해야 함 |
| `unordered` | 순서는 달라도 기대 호출이 일치해야 함 |
| `subset` | 실제 호출이 허용 목록의 범위 안에 있어야 함 |
| `superset` | 실제 호출에 필수 호출이 모두 포함되어야 함 |

필수 Tool 검증에는 `superset`을 사용할 수 있다. 추가 조회가 허용되는 경우에도 필요한 호출이 모두 포함되었는지 확인할 수 있다. 반대로 금지된 Tool 실행을 잡으려면 `subset` 검사를 별도로 적용해야 한다.

호출 목록 비교와 인자 비교는 분리할 수 있다. Tool 이름만 확인할 때는 인자를 무시하고, 계좌·금액 같은 핵심 값까지 검증할 때는 기대 인자가 실제 호출에 포함되는지 확인한다.

## 승인 절차 평가

부작용이 있는 Tool은 실행 전 승인 절차를 거칠 수 있다. 승인 평가에서는 다음 조건을 함께 확인해야 한다.

- 기대한 횟수만큼 중단되었는가
- 올바른 Tool이 승인 대상으로 지정되었는가
- 준비한 승인·거절 결정이 순서대로 사용되었는가
- 처리되지 않은 승인 대기가 남아 있지 않은가
- 거절 시 실제 부작용 Tool이 실행되지 않았는가

최종 답변이 올바르더라도 승인 절차가 생략되었다면 별도의 실패로 판단해야 한다.

## LangSmith Dataset과 Experiment

LangSmith Dataset은 입력과 기대 출력을 저장하는 평가용 사례 모음이다. 각 사례는 Example로 관리되며, 입력, 기대 출력, 사례 ID 등의 Metadata를 포함할 수 있다.

Experiment는 Dataset의 각 사례에 Target을 실행하고 Evaluator를 적용한 결과다. 사례별 실제 출력, 점수, 평가 근거, 실행 오류를 확인할 수 있다.

동일한 Dataset을 사용하면 모델·Prompt·Agent 코드 수정 전후를 비교하기 쉽다. Dataset을 변경하면 결과 비교의 기준도 달라지므로, 평가 기준을 수정할 때는 변경 이력을 함께 관리해야 한다.

## 평가 결과 해석

평가 점수는 단독으로 해석하지 않는다. 실패한 사례의 입력, 기대값, 실제 답변, Trace, Tool 기록, 평가자의 근거를 함께 확인한다.

예를 들어 필수 Tool·인자 평가는 실패했지만 허용 Tool 평가는 통과할 수 있다. 이는 허용된 Tool만 사용했지만 금액이나 계좌가 잘못되었다는 의미일 수 있다. 반대로 최종 답변 평가는 통과했지만 실제 외부 작업이 잘못 처리되었을 가능성도 있으므로 답변과 실행 과정을 분리해 평가해야 한다.

## 평가 설계 기준

- 평가 대상이 답변인지 실행 과정인지 먼저 구분한다.
- 정상·실패·경계 사례를 모두 Dataset에 포함한다.
- 기대값과 초기 State를 사람이 검토한다.
- 동일한 Dataset과 평가 기준으로 변경 전후를 비교한다.
- 점수뿐 아니라 평가 근거와 실행 Trace를 함께 보관한다.
- 실행 오류와 평가 오류·미채점을 통과로 취급하지 않는다.
- 실제 데이터 변경이 발생하는 Agent는 답변·Tool·승인·외부 결과를 각각 검증한다.
